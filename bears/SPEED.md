# 속도 개선 메모

2026-10-12 `watch.log` 기준. 현재 코드(Playwright `locator.click()`)에서 좌석 클릭 후 3단계가 약 1.9~3.3초 걸린다.

## 어디서 시간이 쓰이나

| 구간 | 시간 | 비고 |
|---|---|---|
| 목록 발견 → 좌석 클릭 로그 | 0.65~0.78초 | 잔여석이 이미 있을 때 기준. 현재 로그로는 count / evaluate_all / click 중 어디인지 모름 |
| 단계 1 (자동 배정) | 0.7~1.6초 | 사이트가 좌석 클릭 뒤 화면을 그리는 시간이 대부분으로 보임 |
| 단계 2 (수량 +) | 0.1~0.15초 | 문제 없음 |
| 단계 3 (선택 완료) | 1.0~1.9초 | 버튼이 이미 떠 있어도 Playwright 클릭의 "안정될 때까지 대기" 확인이 걸림 |

## 개선 방법 (안전한 것부터)

1. **측정 먼저**: `SeatList.click_available`의 `count`, `evaluate_all`, `click` 앞뒤에 `time.perf_counter()`로 시각을 찍는다. 0.65초가 어디서 쓰이는지 모르는 상태에서 고치면 추측이 된다.
2. **폴링 간격 단축**: `POLL_SEC` 0.3 → 0.1. 좌석이 풀린 뒤 알아채기까지 평균 150ms를 아낀다. 대신 CDP 호출이 늘어난다.
3. **탭 순회 비용 줄이기**: 탭마다 `update_state`(count) + `click_available`(count)로 왕복이 2번이다. 한 번의 `evaluate`로 "목록 개수 + 후보 + 잔여수"를 같이 읽으면 탭당 왕복이 1번으로 준다. 클릭은 그대로 Playwright로 한다.
4. **단계 3 대기 줄이기**: 단계 3만 `click(force=True)`를 쓰면 "안정될 때까지 대기"를 건너뛴다. 실제 마우스 이벤트라 `isTrusted`는 유지된다. 버튼이 아직 비활성이면 눌러도 소용없으므로 `to_be_enabled` 확인이 같이 필요하다. 먼저 단계 3만 바꿔서 로그로 비교한다.

## 한 작업 (2026-10-12)

- `POLL_SEC` 0.3 → 0.1.
- 목록 확인을 `count` + `evaluate_all` 두 번에서 `evaluate_all` 한 번으로 줄임.
- 단계 3만 `to_be_enabled` 확인 + `click(force=True)`.
- 계측 로그 추가: `CDP roundtrip`, `SEAT CLICKED ... read/click ms`, `STEP 3 detail: wait/click`.
- 측정 결과: CDP 왕복은 5~15ms로 병목이 아님. 좌석 읽기 73ms, 클릭 호출 508ms, 단계 3은 wait 16ms인데 click이 1403ms. 즉 Playwright `click()`이 클릭 뒤에 기다리는 시간이 대부분.
- 모든 클릭에 `no_wait_after=True` 적용 (클릭 뒤 화면 이동 대기 생략). **아직 실행해서 확인 안 함.**

## 더 시도해볼 것

1. `no_wait_after=True` 효과 확인: `click` ms가 수십 ms로 줄어야 함. 안 줄면 원인이 다른 곳이니 클릭 안에서 어디서 쓰이는지 다시 쪼갠다.
2. 그래도 느리면 `page.mouse.click(x, y)`로 좌표 직접 클릭 (`getBoundingClientRect`로 좌표만 구함). 호출 1번, `isTrusted` 유지.
3. 감지가 늦다 싶으면 `MutationObserver`로 페이지 안에서 감시. 읽기가 73ms라 지금은 우선순위 낮음.
4. 단계 1~3을 한 번의 호출로 묶는 것은 보류. 클릭 간격이 너무 짧으면 자동화로 눈에 띔.

## 하지 말 것

- **`el.click()` (evaluate 안에서 JS로 클릭)**: 합계가 1.86초 → 1.6초로 약 250ms 줄었지만 `isTrusted === false`라 봇으로 보이기 쉽다. 시도했다가 되돌렸다.
- **단계를 사람 속도 이하로 연달아 누르기**: 클릭 간격이 수십 ms면 자동화로 눈에 띈다. 속도를 더 올리려면 간격은 최소 100ms 이상 랜덤으로 두는 쪽이 낫다.

## 한계

- 단계 1의 대기와 좌석 클릭 직후 화면 전환은 사이트 쪽 시간이라 코드로 줄이기 어렵다.
- 이 사이트의 약관이 자동화를 막을 수 있다. 속도를 올릴수록 계정 제재 위험도 같이 올라간다.
